# DeepSeek 推理模式：论文依据与测试方案

> 研究文档 · 解释「极简系统提示词 → `We need…` 简写思考 → 能力提升」这个现象，并设计能决定 Riot DeepSeek 适配方案的实验。
>
> - **目标模型**：`deepseek-v4-flash`（官方 API，`reasoning_effort=max`）
> - **日期**：2026-10-18
> - **性质**：第 1、2 节是论文摘录和试点数据，第 3–6 节是**尚未执行**的方案。
> - 试点脚本与原始数据在会话 scratchpad（`probe2.py`、`exp1–4.py/json`），正式执行时应搬进 `scripts/` 下的独立目录。

---

## 1. 论文里和这个现象有关的事实

按时间顺序。每条只摘和「系统提示词 / 推理风格 / 是否思考」相关的部分。

### 1.1 DeepSeek-R1（arXiv 2501.12948；Nature 补充材料 §2.3.2）

- **R1-Zero 用「we」或干脆不用主语，R1 更常用「I」。** 补充材料原话：R1-Zero "is more likely to employ the pronoun 'we' or avoid first-person pronouns altogether"。R1 的冷启动数据是**人工把 R1-Zero 的思考改写成口语化、第一人称**，再让 LLM 照样改写更多数据；动机写明是「产品驱动」。
- 冷启动偏好的结构：先理解问题，再带反思和验证的详细推理。
- **语言一致性奖励**：按思维链里目标语言词的比例给奖励，论文承认会让性能「轻微下降」，为了可读性仍然保留。
- 局限：few-shot 会降低性能，推荐零样本直接描述问题和输出格式；模型卡建议不用系统提示词。
- 非推理数据（写作、问答、自我认知）复用 V3 的 SFT 数据；简单问候类请求不配思维链（arXiv v1 §2.3.3）。

**推论**：`We need answer. Need compute.` 这种电报体是**纯 RL 长出来的原生推理风格**（R1-Zero 一脉）；`The user wants… Let me…` 是**为产品体验改写过的风格**。

### 1.2 DeepSeek-V3（arXiv 2412.19437 §5.1、§5.4.1）

- 推理数据来自各领域专家（代码、数学、通用推理），每个专家先 SFT 再 RL，然后拒绝采样产出最终 SFT 数据。
- **每条推理数据生成两种 SFT 样本**：`<问题, 原始回答>` 和 `<系统提示词, 问题, R1 回答>`。后者的系统提示词专门要求回答带反思和验证。RL 阶段再用高温采样让 R1 模式「在没有显式系统提示词时」也出现。
- 蒸馏 R1 提升了准确率，但回答长度大约翻倍（MATH-500：769 → 1510 token）。V3 刻意控制了输出风格和长度。

**推论**：从 V3 开始，DeepSeek 就在用**系统提示词作为风格/模式的条件开关**。

### 1.3 DeepSeek-V3.1（模型卡）

- 思考 / 非思考由模板里的 `<think>` / `</think>` 决定。
- **工具调用只在非思考模式下支持**；搜索 agent 有一套专门的思考模式格式。

**推论**：上一代模型里，「带工具调用指引的系统提示词」大量配的是**非思考**轨迹。

### 1.4 DeepSeek-V3.2（arXiv 2512.02556 §3、§3.2、附录 B）

- 冷启动：**不同任务的 prompt 配不同的系统提示词**（§3.2.2）。推理数据的系统提示词很短（"Please first reason before giving the final answer"，附录表 6）；非推理的 agent 数据，系统提示词是工具调用指引（表 7）；「推理中多次调工具」又是另一套（表 8）。
- 专家蒸馏：每个领域一个专家，思考模式和非思考模式的数据由**不同模型**生成。
- 混合 RL：推理和 agent 任务用规则奖励 + 长度惩罚 + 语言一致性奖励；通用任务用按 rubric 打分的生成式奖励模型。
- 合成 agent 任务的 RL 消融只在**非思考模式**下做（§4.3）。
- 思维链在工具轮之间保留，新的用户消息到来时丢弃（§3.2.1）。

### 1.5 DeepSeek-V4（arXiv 2606.19348 §5.1–5.3）

- 三种模式（表 2）：Non-think 直接 `</think>` 加回答；Think High；Think Max 在系统提示词**最前面**插一段固定指令（表 3，开头是 "Reasoning Effort: Absolute maximum with no shortcuts permitted"），RL 时给更宽的长度惩罚和上下文。
- 工具调用的系统提示词（表 4）要求「先在 `<think>` 里写完整推理，再调工具」。
- 后训练：先训十多个领域专家（数学、代码、agent、指令遵循……），每个都是 SFT 加 GRPO；再用**在线蒸馏**（反向 KL，全词表 logits）合成一个学生模型。学生「按当前任务语境」对齐相应的专家（§5.1.2）。
- 智能体场景下，推理跨工具轮、跨用户轮都保留；普通对话里，新用户消息到来时丢弃。
- 评测：温度 1.0，三种模式的上下文分别是 8K / 128K / 384K。

## 2. 试点观察（约 400 次采样，只看开头风格和调工具前的推理长度）

| 模式 | 特征 | 什么时候出现 |
|---|---|---|
| A 简写规划 | `We need … Need …`，省冠词；调工具前推理很长 | 一句话 persona、无系统提示词、1.5 万字无规则文本；数学题几乎总是 |
| B 叙述 | `The user wants… Let me…`；推理较短 | 产品化规则 / 身份描述；中文闲聊几乎总是 |
| C 不思考 | `reasoning_tokens = 0`，直接调工具 | Riot 完整提示词 + 画 SVG（4/4）；Riot 身份段 + 修 bug（4/4） |
| D 流畅解题 | `We need to count…`，语法完整 | 仅 Riot 完整提示词 + 数学（n=3） |

已经定位的触发因素：

- **自报模型名**（`powered by deepseek-v4-flash`）把修 bug 任务从 A 推到 B（8/8）；换成 `gpt-5` 没有这个效果。
- 和长度无关，和 `agent` / `coding` 这类字眼无关，和单条 NEVER 规则无关。
- 把 Riot 规则放进**用户消息里任务的后面**（`<system-reminder>` 包裹），系统提示词只留一句 persona：后置放法 8/8 是 A（SVG 4/4、修 bug 4/4）；放在任务前面时 SVG 4/4 是 A，修 bug 只有 1/4 是 A。

**试点没有测的**：最终产物质量、规则遵守、多轮稳定性。「A 模式更强」目前只有用户自己的主观实验支撑。

## 4. 实验工具

在 scratchpad 原型的基础上搭一个独立的小工具（Python 就够，不进 Riot 主代码）：

1. **单步探针**（已有）：流式读到第一个工具调用或正文为止，记录调工具前的全部推理、`reasoning_tokens`、首事件类型。
2. **完整轨迹执行器**（新增）：在临时目录里真正执行 `Read / Write / Edit / Bash / Glob`，循环到模型不再调工具或达到步数上限；每一步都回传 `reasoning_content`，和 Riot 的 `replay_reasoning` 行为一致。
3. **风格分类器**：
   - 零推理 → C；
   - 冠词 / 功能词比例 < 6% → A；
   - 以 `We need to` 开头且语法完整 → D；
   - 其余 → B。
   - 另外记录：`we / I / the user` 的人称计数，思维链语言（中文字符比例），首段是否先复述任务。
   - 抽 50 条人工标注，校准分类器，报告一致率。
4. **固定参数**：温度 1.0（如果 API 在思考模式下忽略温度，就记录这一点）；`max_tokens` 足够大，避免截断污染长度统计；每个请求记录缓存命中情况。

## 5. 实验设计

### E1 模式地图复现（便宜，只看单步）

- **因子**：系统提示词 12 种 × 任务 6 种 × 有无工具 2 种，每格 n=8。
- **系统提示词**：无 / 一句 persona（英文、中文）/ Riot 完整 / Riot 去模型名 / Riot 只留身份段 / 长度匹配的中性文本 / 规则密集短文 / V4 表 4 工具规则 / V3.2 表 6 推理指令 / Think Max 前缀 / 规则后置到用户消息。
- **任务**：数学、算法代码、画 SVG、修 bug（agent）、中文闲聊、中文技术问答。
- **产出**：模式分布热图、调工具前推理长度的分布。检验 H2、H4（用多项逻辑回归做方差分解）。

### E2 机制拆解（每条单独开，n=12）

- **H1**：在 A 和 B 的样本上统计人称和句式特征，看是否和 R1-Zero / R1 的描述一致。
- **H3**：从 Riot 完整提示词出发逐节删除（共 21 节），记录 C 的比例变化，找出贡献最大的几节；再测「完整提示词 + V4 表 4 那句」。
- **H5**：`effort=high` / `max` / `max + 手动 Think Max 前缀`，在数学子集上比较推理长度和准确率。
- **H6**：同一批题，分别用中、英文的任务和系统提示词，比较思维链语言和准确率。

### E3 能力对比（核心，检验 H8）

**四个候选配置**：

| 配置 | 系统提示词 | 规则放哪 |
|---|---|---|
| R0 现状 | Riot 完整 | 系统提示词 |
| R1 极简开局（当前未提交代码） | 首轮一句 persona，之后完整 | 系统提示词 |
| R2 规则后置 | 一句 persona | 首条用户消息，任务之后，`<system-reminder>` 包裹；去掉模型名 |
| R3 最小改动 | Riot 完整，去掉模型名，开头加 V4 表 4 那句 | 系统提示词 |

**任务集**（全部可以自动判分，主观任务单列）：

- **数学** 40 题：公开竞赛题，有标准答案；每题 2 次采样，按 sympy 判等。
- **算法代码** 30 题：自带单元测试，本地执行判分。
- **Agent 修 bug** 15 个：小型 Python 仓库，人为植入 bug，以测试通过为准；记录步数、工具调用次数、总 token。
- **改已有代码** 10 个：带「只改要求的部分」约束，用 diff 范围判分（检查越界修改）。
- **设计类** 10 个（SVG / 单页 HTML）：两两盲评，交换左右位置各评一次，评审用不同家族的模型，再抽 20% 人工复核。

**统计方法**：配对比较（同题不同配置），准确率用 McNemar 检验，连续指标用 bootstrap 95% 置信区间。事先约定主要指标是「agent 修 bug 通过率」，其余为次要指标，避免挑数据。

### E4 规则遵守与多轮稳定性（检验 H7）

- 3 轮对话脚本 × 10 个，用 R0–R3 四个配置各跑一遍。
- **自动核对的 Riot 规则**：回答语言跟随用户（中文）、本地文件用链接格式、不主动 commit、改动后跑测试、引用代码的格式。
- 记录每一轮的推理模式，看 A 模式能否从首轮延续下去。对照组：关掉 `replay_reasoning`。

## 6. 决策规则（事先定好）

- **采用 R2**：如果它在主要指标上不低于 R0（单侧检验，非劣效界 3 个百分点），在次要指标里至少两项更好，并且规则遵守率不低于 R0 的 95%。
- **R3 作为保底**：如果 R2 的规则遵守率不达标，但 R3 就能消除 C 模式并提升指标，就采用 R3。这个改动小，对其他模型无影响。
- **放弃 R1（当前极简开局 + 丢弃重发）**：除非它在指标上显著优于 R2。原因是它的纯文字分支会白跑一次最高档请求。
- **全部无差异**：保持 R0，只去掉模型名（试点里已有明确的负面效应）。

## 7. 成本与顺序

- E1 约 1150 次单步调用，E2 约 600 次；单步在首个工具调用处截断，token 很少。
- E3 是大头：约 105 题 × 4 配置 × 1–2 次，agent 任务按 30 步、每步 20K 上下文估算，大部分是缓存命中的输入。
- **顺序**：E1 → E3（先回答「值不值得改」）→ E4 → E2（机制拆解只在需要写进注释、说服自己时做）。

## 8. 执行结果（2026-10-18，E1 + E3）

工具在 [`scripts/deepseek-modes/`](../../scripts/deepseek-modes/)：`e1.py` / `e1_report.py`，`e3.py` / `e3_report.py`，`design_review.py`。结果写在 `results/`，不进版本库。

### 8.1 和方案的偏差

- **风格分类器改了**：冠词比例在数学推理上不可靠（变量 `a`、公式会干扰），改成按句式判断：句首的 `Need …`，或者不接 `to` 的 `We need …`，就是 A。E1 用存下的开头文本重新分类。
- **数学题不给工具**，只测纯推理。R1 在没有工具时不会触发丢弃重发，所以数学上 R1 等于「全程一句 persona」。
- **样本量比方案小**：仓库任务每个配置跑 2 次，代码和设计题每个配置 1 次。
- **设计题评审只有一个人**：Claude，和被测模型不是同一家族。没有交换左右位置的二次评分，也没有人工复核。
- 温度 1.0，`reasoning_effort=max`，单次输出上限 32K。工具只有 5 个（Read / Write / Edit / Bash / Glob），Bash 跑在 `sandbox-exec` 里，不能联网，工作目录以外不能写。

### 8.2 E1：模式地图（12 种系统提示词 × 6 种任务 × 有无工具，n=8，共 1152 次）

带工具时，每格的「A 数 / C 数」（A 是简写，C 是不思考）：

| system | math | algo | svg | bug | chat_zh | tech_zh | A 合计 |
|---|---|---|---|---|---|---|---|
| none | 8/0 | 1/0 | 6/1 | 0/5 | 0/0 | 0/0 | 15 |
| **persona** | 8/0 | 8/0 | 8/0 | 8/0 | 8/0 | 8/0 | **48** |
| persona_zh | 8/0 | 8/0 | 8/0 | 8/0 | 4/0 | 3/0 | 39 |
| **riot_full** | 6/0 | 0/0 | 0/7 | 0/8 | 0/0 | 0/0 | **6** |
| riot_no_model | 3/0 | 0/0 | 0/3 | 0/6 | 0/0 | 0/0 | 3 |
| riot_identity | 8/0 | 0/0 | 0/7 | 0/8 | 0/1 | 0/0 | 8 |
| filler_len_matched | 8/0 | 8/0 | 7/0 | 0/0 | 0/0 | 1/0 | 24 |
| rules_dense | 7/0 | 2/0 | 5/0 | 0/6 | 0/0 | 0/0 | 14 |
| v4_tool_rule | 8/0 | 7/0 | 5/0 | 0/1 | 0/0 | 0/0 | 20 |
| r32_reason | 8/0 | 8/0 | 7/0 | 4/1 | 2/0 | 6/0 | 35 |
| think_max | 8/0 | 7/0 | 8/0 | 2/0 | 0/0 | 1/0 | 26 |
| **rules_in_user** | 8/0 | 8/0 | 8/0 | 8/0 | 5/0 | 4/0 | **41** |

结论：

1. **「一句 persona + 工具」是最强的触发条件**：48/48。不给系统提示词反而只有 15/48，修 bug 时 5/8 不思考。所以要的不是「越少越好」，而是**像那一类训练数据的开头**。
2. **工具会改变选择**：不给工具时，none、filler、think_max 在多数任务上都是 A（各 40+/48）；一加工具，闲聊和技术问答类就落回 B。
3. **Riot 完整提示词在带工具时几乎从不进 A**（6/48），而且画 SVG、修 bug 时大多直接不思考。去掉模型名也没有改善（3/48）。试点里「模型名是触发器」的结论只在小样本上成立，放大样本后，主因是 Riot 的**规则语体本身**。
4. **H2 部分成立**：长度匹配的无规则文本保持 A（24/48，不带工具时 40/48），规则密集的短文变成 B/C。语体比长度更重要。
5. **H3 不成立**：V4 表 4 那句「先推理再调工具」**不能**消除 C。E3 里 R3 修 bug 任务的首步仍然 30/30 是 C。
6. **H5 没有检验**：E1 只跑了 max 档，没有 high 档做对照。另外，把 Think Max 那段话单独用作系统提示词时，带工具 A 是 26/48（无系统提示词时是 15/48），不带工具 A 是 44/48。
7. **H1 成立**：在 E1 的全部开头文本里，A 每 100 词用「we」5.2 次、「I」0.3 次；B 用「I」4.9 次、「we」0.1 次，80% 以「The user」开头。这和 R1 补充材料对 R1-Zero（用 we 或不用主语）与 R1（用 I）的描述一致。「I」的差异和分类规则无关，不是循环论证。

### 8.3 E3：能力对比（四个配置，共 680 条轨迹）

**正确率全部撞了天花板**：

| 组 | R0 现状 | R1 极简开局 | R2 规则后置 | R3 最小改动 |
|---|---|---|---|---|
| 修 bug（15 个 × 2） | 30/30 | 30/30 | 30/30 | 30/30 |
| 限定范围改代码（10 个 × 2） | 19/20 | 20/20 | 20/20 | 20/20 |
| 算法代码（30 个） | 30/30 | 30/30 | 30/30 | 30/30 |
| 数学（40 题 × 2，修正提取器后） | 72/80 | 75/80 | 71/80 | 72/80 |

- R0 唯一一次没过的改代码任务，是**改了测试文件**。

### 8.4 按第 6 节的决策规则

- 主要指标（修 bug 通过率）四个配置都是 100%，**撞了天花板，没法判断非劣效**，这一轮不能据此做决定。
- 次要指标里，R2 在设计质量上明显更好，在改代码的范围遵守上与其他配置持平，成本有升有降。
- 当时规则遵守率还没测，所以没有下结论。E4 的结果和最终决定见 8.5、8.6 节。
- R3（去模型名 + V4 工具规则）**没有达到目的**：C 模式照旧，可以放弃。

### 8.5 E4：多轮规则遵守（10 个三轮中文对话 × 6 个配置 × 2 次，共 120 段对话）

工具是 `e4.py` / `e4_report.py`。每段对话都在一个 git 仓库里进行（复用 E3 的 bug 仓库）：

- 第 1 轮用中文让它修 bug；
- 第 2 轮加一个小功能；
- 第 3 轮问「某某是怎么实现的，把代码给我看」。

每轮自动核对 Riot 的五条规则：

- **中文回答**：代码以外的正文里，中文字符占比要超过 30%。
- **文件链接**：正文里提到的工作区文件，每个都要至少有一处 Markdown 链接指向它。这个口径比较严，写成反引号的 `cache.py` 也算违规。
- **不擅自 git**：没有 commit / push / stash / reset 等命令，提交数也没变。
- **改后验证**：本轮改了文件的话，最后一次 Write/Edit 之后要跑过 python 或测试。
- **引用格式**：只在第 3 轮核对。引用已有代码要用 ```` ```起始行:结束行:路径 ````，并且行号对得上；新写的代码不许用这个格式。

另加两个**关掉思维链回传**的对照组：R1-noreplay 和 R2-noreplay。做法是把上一条用户消息之前的助手消息里的 `reasoning_content` 去掉，当前轮的工具循环里照常回传。核对器的判断我人工抽查过（英文回答、引用格式、链接各看了几条），都判对了。

| 配置 | 中文回答 | 文件链接 | 不擅自 git | 改后验证 | 引用格式 | **合计** | 三轮后测试仍通过 |
|---|---|---|---|---|---|---|---|
| R0 现状 | **37/60 62%** | **30/47 64%** | 60/60 | 40/40 | 19/19 | **186/226 82%** | 20/20 |
| R1 极简开局 | 60/60 | 44/49 90% | 60/60 | 40/40 | 20/20 | 224/229 98% | 20/20 |
| **R2 规则后置** | 60/60 | 49/50 98% | 60/60 | 40/40 | 20/20 | **229/230 100%** | 20/20 |
| R3 最小改动 | 51/60 85% | 38/43 88% | 60/60 | 40/40 | 20/20 | 209/223 94% | 20/20 |
| R1-noreplay | 60/60 | 40/47 85% | 60/60 | 40/40 | 19/19 | 219/226 97% | 20/20 |
| R2-noreplay | 60/60 | 48/48 | 60/60 | 41/41 | 20/20 | 229/229 100% | 20/20 |

结论：

1. **R2 的规则遵守率不低于现状，反而更高**：合计 100%，现状是 82%（R2 是 R0 的 121%）。
2. **现状的主要问题是用英文回答中文用户**：R0 每一轮约有 40% 用英文回答，R3 约 15%。系统提示词全是英文、只有用户消息是中文时，叙述模式和不思考模式会跟着系统提示词的语言走；规则后置之后，用户消息里中文和规则混在一起，模型就跟着中文走了。
   - 需要说明：实验用的提示词没有用户自定义指令（`extra` 为空），真实使用中如果用户写了「用中文回答」，R0 的这个差距可能会缩小。
3. **不擅自 git、改后验证、引用格式**：六个配置全部满分，在这组任务上分不出高下。
4. **H7 成立：思维链回传能把首轮的模式带下去**。每轮第一步的推理模式：

   | 配置 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
   |---|---|---|---|
   | R0 | C20 | B20 | B20 |
   | R1（回传） | A20 | A20 | A18 B2 |
   | R1-noreplay | A20 | **A1 B19** | **B20** |
   | R2（回传） | A20 | A20 | A20 |
   | R2-noreplay | A20 | A20 | A20 |

   R1 只在首轮换系统提示词，模式**全靠回传的思维链延续**，关掉回传后第 2 轮就掉回叙述模式。R2 每轮的系统提示词本身就是 persona，所以不依赖回传。R2 在全部步骤里 A 的占比也最高：三轮分别是 85% / 74% / 100%，R0 是 1% / 0% / 0%。
5. **成本**：每段对话 completion token 的中位数是 R2 2998、R1 2140，R0 4269、R3 4472。R2 比现状省约 30%。

### 8.6 按第 6 节的决策规则：采用 R2

- **主要指标非劣效**：修 bug 通过率 R2 和 R0 都是 30/30，E4 三轮之后测试仍通过也都是 20/20。观测值不劣，但因为撞了天花板，这一条**提供的信息很弱**。
- **至少两项次要指标更好**：成立。
  - 设计质量：盲评 21 分对 6 分，p≈0.04；
  - 规则遵守率：100% 对 82%；
  - 多轮对话成本：低约 30%。
- **规则遵守率不低于 R0 的 95%**：成立，是 R0 的 121%。

**结论：按事先约定的规则，采用 R2。** 也就是：DeepSeek 的系统提示词只放一句 persona，Riot 规则用 `<system-reminder>` 包起来放到首条用户消息里任务的后面，并去掉模型名。同时放弃 R3，现有的 R1 实现（极简开局 + 纯文字就丢弃重发）也被 R2 取代，因为 R2 遵守率更高，又不需要丢弃重发。

落地前要注意：

- **规则只在首条用户消息里出现一次**。压缩历史（compaction）时如果首条消息被总结掉，规则就丢了。实现时要在压缩后重新注入，或者每轮在 `<system-reminder>` 里带一份。后一种做法会影响前缀缓存，需要权衡。
- **本轮没测**的东西：长会话（几十轮以上）、压缩之后的情况、子 agent、用户自定义指令和 R2 叠加时的效果。
- 设计质量的证据只有一个评审、9 道题。

### 8.7 R2 落地与真实请求回归

**实现**：在 `crates/riot-kernel/src/adapt/rules_in_user.rs` 里加了一个 provider 包装，只包主循环，取代原来的 `MinimalOpening`。它在**每次请求时**做三件事：

- 把系统提示词换成 persona；
- 把原系统提示词去掉缓存边界标记，包成 `Attachment::SystemReminder`，接在首条用户消息末尾；
- 历史本身不改。

这样处理有三个结果：

- **压缩后规则不会丢**：压缩之后首条消息变成总结，规则会自动贴到新的首条消息上。
- **前缀缓存跨轮不变**：`两轮之间请求前缀逐字节不变` 这个测试照样通过。
- **压缩总结、分叉、子 agent 不受影响**：它们照旧用完整的系统提示词。

**模型名保留**：另测过规则后置时去掉模型名的效果（各 8 次）：

- agent 类任务（画 SVG、修 bug、写算法）两种写法都是 24/24 简写；
- 只有中文闲聊的简写比例从 5/8 降到 1/8。

「被问是什么模型时答得上来」是已有的产品要求，所以保留模型名。

**真实请求回归**：从 `两轮之间请求前缀逐字节不变` 测试里导出 Riot 真实装配的 OpenAI 线上请求（23 个工具，首条消息依次是时钟提醒、原话、规划提醒、规则），换上测试任务，每格 8 次：

| | 画 SVG | 修 bug | 写算法 |
|---|---|---|---|
| R2（实际实现） | A8 | A2 B5 C1 | A8 |
| 规则放回系统提示词（相当于 R0） | A7 B1 | A0 B4 C4 | A0 B8 |

修 bug 远低于实验里的 8/8，原因拆出来是**工具描述**。同一条首条消息（各 8 次）：

- 配 5 个精简工具时 7/8 是简写，配 23 个真实工具时只有 3/8；
- 去掉时钟提醒或规划提醒都没有明显变化。

所以前面所有实验（都只带 5 个精简工具）高估了 R2 在修 bug 类任务上的效果，但 R2 相对现状仍然更好。

**工具描述消融**（`tool_ablation.py`，真实 R2 请求形状，修 bug 任务，两轮合并）：

| 工具组合 | 工具数 | 工具定义总字符 | 首步简写 A |
|---|---|---|---|
| 精简 5 个（实验用的） | 5 | 1.2K | 37/40（93%） |
| Riot 的 5 个核心工具，描述和参数说明都缩成一句话 | 5 | 2.2K | 18/24（75%） |
| Riot 全部 23 个，描述和参数说明都缩成一句话 | 23 | 11.5K | 19/40（48%） |
| Riot 的 5 个核心工具，原样长描述 | 5 | 18.3K | 14/40（35%） |
| Riot 全部 23 个，原样（基线） | 23 | 52.8K | 13/40（33%） |
| 23 个，只缩描述、参数说明不动 | 23 | 18.6K | 5/16 |
| 去掉 6 个产品类工具（TodoWrite、CreatePlan 等） | 17 | 34.8K | 6/16 |

结论：

1. **主因是描述文字，不是工具数量，也不是工具种类**。同样 5 个工具，长描述 35%，缩短后 75%。去掉产品类工具没有改善。
2. **参数说明也算**：只缩工具描述、参数说明不动时，还剩 18.6K 字符，没有改善。
3. **量越大越差，但到一定程度就饱和了**：大约 2K 时是 75%，11K 时 48%，18K 以上稳定在 33–35%。5 个工具配长描述（18K）和 23 个原样（53K）一样差。
4. 23 个缩短版（11.5K）比 5 个缩短版（2.2K）差，这里**数量和总量是混在一起的**，分不开。
5. 写算法任务抽查：缩短描述前后都是 7/8，不会把本来就好的任务带坏。

这只说明了推理模式受影响。描述里写着用法约束（比如 Bash 的「长期运行的进程 MUST 设 `background: true`」），把描述砍短，工具很可能被用错，这个代价还没测。

### 8.8 E5：工具说明后置（真实工具定义，完整轨迹）

工具是 `agent_real.py` / `e5.py` / `e5_report.py`。所有配置都是 R2 的形状，带 Riot 真实的 23 个工具：

- Read / Write / Edit / Bash / Glob / Grep / Delete / Terminal* 按 Riot 的 schema 真的执行；
- 其余工具给桩：TodoWrite 回执，AskUserQuestion 回「用户不在」，其他回「本环境不可用」。

三个配置：

- **T0**：工具定义原样，就是现在的实现；
- **T1**：工具定义只留一句话描述、参数去掉说明，完整说明作为 `tool_reference` 一节放进首条消息的 reminder；
- **T2**：工具定义同 T1，但完整说明哪里都没有。

12 道任务，每个配置各跑 2 次，共 72 条轨迹：

- 6 个修 bug；
- 2 个限定范围的改代码；
- 4 道专门触发工具约束的题：起开发服务器（要用 `background`）、删一个没人用的文件（要用 Delete）、找某段逻辑在哪一行（要用 Grep）、跨文件改名（不许用 `sed -i`）。

违规按工具描述里写明的约束自动记录：用 shell 搜索、读写文件，覆盖前没 Read，Edit 带行号前缀，长期进程没设 background，用 `rm` 删单个源文件，单独一条 `cd`，主动写文档文件。

| 配置 | 通过 | 首步简写 A | 全部步骤 A | 每条轨迹的违规数 | 有违规的轨迹 | completion tokens 中位数 |
|---|---|---|---|---|---|---|
| T0 原样 | 24/24 | 8/24 | 36% | 0.46 | 6/24 | 1015 |
| T1 说明后置 | 24/24 | 8/24 | 41% | 0.33 | 7/24 | 1010 |
| T2 只剩一句话 | 24/24 | **14/24** | **55%** | **1.21** | **15/24** | 1101 |

违规主要是用 `find` 找文件（T0 7 次、T1 7 次、T2 19 次）和用 `cat` 读文件（T0 1 次、T1 1 次、T2 7 次）。三个配置都正确设置了 background，改代码任务的范围也都遵守了。

结论：

1. **说明后置没有用**：T1 的推理模式和 T0 几乎一样。和 Riot 规则不同，工具说明挪到消息侧救不回模式。可能的原因是首条消息里一下子多了约 5 万字的工具手册，整条消息都成了产品文档；这只是推测，没有拆开测。
2. **把说明彻底删掉能换回一部分模式，代价是工具纪律变差**：T2 的简写比例升到 55%，但违规数是 T0 的 2.6 倍，主要是退回到用 shell 找文件、读文件。正确率三者都是 100%，所以这一轮用纪律换模式，换不到可测的收益。
3. 每格 24 次，首步 A 的 14/24 对 8/24 只是边缘显著（p≈0.08），模式结论要打折看。
4. **决定**：保持 T0，也就是现在的 R2 实现，工具定义不动。

### 8.9 参考 DeepSeek Harness 与 V4.1（E6，单步探针）

**DeepSeek Harness 里的事实**（`deepseek-ai/deepseek-harness`，2026-08 开源；只读了源码和快照，没有执行）：

- **`minimal` 预设就是 RL 训练用的 agent 组合**。内部笔记 `2026-08-10-minimal-preset-owns-rl-composition` 称它为「Claude SWE-compatible RL agent」：
  - 系统提示词只有 `You are a helpful software engineer assistant.`，并且会强制清掉其他所有提示词片段和运行时上下文；
  - 2026-09 起只剩**一个持久化的 bash 工具**（笔记 `minimal-profiles-persistent-shell-only`），没有编辑器，没有历史压缩。
- **RL 版 bash 的描述只有 6 行**，而且语义和 Riot 的 Bash 正好相反：
  - shell 状态在多次调用之间保留（Riot：每次调用相互独立，`cd` 不延续）；
  - 用 `sed -n 10,25p` 查看文件（Riot：绝不要用 `sed`/`cat` 读文件）；
  - 长期运行的命令用 `&` 放后台（Riot：设 `background: true`）。
- **DeepSeek 自家的产品预设**，系统提示词同样有 27–42K 字符。也就是说，规则后置不是 DeepSeek 自己的做法，是这里实测出来的。
- **官方适配器**：
  - 默认单次输出上限 256K；
  - 每一轮的思维链都原样回传；
  - V4.1 Flash（`deepseek-flash`）的端点支持在历史中途追加 system 消息（`systemPromptUpdate: in-history`）和新增工具（`toolUpdate: addition-only`），两者都不会打掉前缀缓存。
- 另外，`deepseek-flash` 和 `deepseek-v4-flash` 被问到「你是什么模型」时都说自己是 ChatGPT。

**E6 探针**（`e6_probe.py`，真实 R2 请求形状，带工具，单步）：

| 变体 | 修 bug | 画 SVG | 写算法 |
|---|---|---|---|
| 现状 R2，V4 Flash | 1/24 | 8/8 | 8/8 |
| 现状 R2，V4.1 Flash | 2/24 | 8/8 | 8/8 |
| 纯 RL 环境（persona + RL 版 bash，无规则），V4 / V4.1 | 8/8、8/8 | 8/8、8/8 | 8/8、8/8 |
| **R2，Riot 的 Bash 换成 RL 版 bash**，V4 | **12/24** | 8/8 | 7/8 |
| R2，Bash 换成 RL 版，V4.1 | 12/24 | — | — |
| R2，系统提示词前加 Think Max 指令 | 0/8 | 8/8 | 5/8 |

结论：

1. **最大的单一因素是 Bash 的描述**。只换这一个工具的描述，修 bug 的简写比例就从 4% 升到 50%（各 24 次）。Riot 的 Bash 描述有 3441 字，里面的禁令（不许用 shell 读文件、搜索，`cd` 不延续）和 RL 训练时的 bash 语义正面冲突。
2. **V4.1 Flash 在模式上和 V4 没有可测差异**。
3. **Think Max 指令没用**，写算法还变差了，排除。
4. 纯 RL 环境是 100%，R2 加 RL bash 是 50%。剩下的差距来自其余 22 个工具的描述和规则 reminder。

**注意**：直接把描述换成 RL 版是不对的。RL 版写着「状态持久」「用 `&` 放后台」，而 Riot 的 Bash 实际上每次调用相互独立，模型会照着描述去依赖 `cd` 延续，然后出错。要用 RL 版描述，Bash 的**行为**也得改：跨调用保留 cwd 和环境变量，正确处理 `&` 放后台的进程。另外，模型用 `sed`、`cat` 改文件的话，Riot 的改动追踪（检查点、diff 界面）就拿不到这些改动，这也是产品层面的代价。

### 8.10 E7：RL 式 Bash（模拟持久 shell，完整轨迹）

工具是 `agent_real.py`（持久 shell、改动追踪、后台存活检查）、`e7.py`、`e7_report.py`。

**持久 shell 的模拟方式**：每次调用前恢复上一次的 cwd 和导出的环境变量，调用后再保存；用 `&` 放后台的进程不阻塞，一直活到任务结束。shell 函数和未导出的变量不保留。

**改动追踪的统计方式**：每次 bash 调用前后给工作区拍快照，看最终改动的代码文件里，有多少是 shell 直接改的、绕开了 Write/Edit/Delete。

四个配置，都是 R2 的形状加 Riot 真实的其余 22 个工具：

- **T0**：现状，Riot 原样的 Bash，一次性 shell，长期进程用 `background` 参数；
- **B1**：RL 版原文，工具名是小写 `bash`，持久 shell；
- **B2**：按 Riot 需要改写的 RL 写法，工具名 `Bash`，持久 shell，补了一条「破坏性操作先问」；
- **B3**：B2 再加一句「改文件用 Edit/Write，方便用户看 diff」。

12 道任务（同 E5）× 4 个配置 × 3 次。起服务那题按「结束时服务还活着、回答里有地址」判。B1 有一条轨迹卡在执行器里（模型开了一个 `screen` 会话），记为执行器故障剔除，有效 143 条。

| 配置 | 通过 | 首步简写 A | 全部步骤 A | 代码改动走 Riot 工具的比例 | 调用不存在的工具 | completion tokens 中位数 |
|---|---|---|---|---|---|---|
| T0 现状 | 36/36 | 10/36（28%） | 30% | 100%（39/39） | 0 | 1074 |
| **B1 RL 原文** | 35/35 | **19/35（54%）** | **52%** | 100%（39/39） | **44** | 1118 |
| B2 Riot 版 RL 写法 | 36/36 | 14/36（39%） | 41% | 100%（39/39） | 0 | 948 |
| B3 B2 + 改文件用 Edit | 36/36 | 12/36（33%） | 34% | 100%（39/39） | 0 | 989 |

只看 6 个修 bug 任务的首步简写：T0 2/18，B1 6/18，B2 1/18，B3 1/18。

结论：

1. **正确率不受影响**，四个配置都是 100%。
2. **改动追踪的担心没有发生**：持久 shell 加「用 sed 查看文件」的描述，模型也**从不用 shell 改代码**，代码改动 100% 走 Write/Edit/Delete。shell 只是更多地用来 `find` 和 `cat` 查看文件（B 系列 find 16–20 次，T0 8 次）。所以 B3 那句「改文件用 Edit」是多余的，还会削弱效果。
3. **推理模式只有原样的 RL 文本提升明显**：B1 首步简写从 28% 升到 54%（p≈0.03）。按 Riot 需要改写过的 B2 只到 39%，修 bug 上没有提升。原文措辞和小写的 `bash` 名字本身就是信号。
4. **B1 的硬伤是工具名**：Riot 的规则文字里写的都是 `Bash`，模型 44 次调用了不存在的 `Bash`。落地时要把 `Bash` 当作 `bash` 的别名接受。
5. **执行器的教训**：模型为了让服务一直跑，会用 `nohup`、`setsid`、`screen` 把进程放进新会话，按进程组清理够不着。已经改成按工作目录兜底清理，并给每条轨迹加了 20 分钟的总时限。

**建议**：如果要改 riot-tools，DeepSeek 下用一个专用的 `bash` 工具：

- **描述原样**使用 RL 版（只在末尾补一条「破坏性操作先问」，补完需要回归确认效果没掉）；
- 具备**持久 shell 语义**（cwd、环境变量跨调用保留，`&` 放后台的进程由 Riot 托管和回收）；
- 接受 **`Bash` 作为别名**；
- 其余工具不动。

### 8.11 E8：RL 式 bash 落地前回归

`e8.py`，同一批 12 道任务，每个配置 3 次，同期重跑 T0 作对照，共 108 条，全部有效。执行器已经加上按工作目录兜底清理和 20 分钟时限，没有轨迹超时，也没有进程残留。

- **B1a**：RL 版原文，工具名 `bash`，持久 shell；对 `Bash` 的调用按别名接受。
- **B4**：B1a 再在描述末尾补一条「Ask the user before destructive operations they did not request, such as `git push --force`, `git reset --hard` or `rm -rf` outside build output.」

| 配置 | 通过 | 首步简写 A | 全部步骤 A | 修 bug 首步 A | 调用不存在的工具 | 走别名 | 长期进程没放后台 | 代码改动走 Riot 工具 | completion tokens 中位数 |
|---|---|---|---|---|---|---|---|---|---|
| T0（同期） | 36/36 | 6/36（17%） | 27% | 0/18 | 0 | 0 | 0 | 100%（39/39） | 950 |
| B1a | 36/36 | 20/36（56%） | 53% | 5/18 | **0** | 86 | 4 | 100%（39/39） | 901 |
| **B4** | 36/36 | **21/36（58%）** | **55%** | **8/18** | **0** | 88 | **0** | 100%（39/39） | 903 |

结论：

1. **模式提升还在，而且更稳**：B4 首步简写 58%，同期 T0 是 17%（p≈0.0005），和 E7 里 B1 的 54% 一致。
2. **工具名错误归零**：别名接住了全部 88 次 `Bash` 调用。模型多数时候仍然叫它 `Bash`（跟着 Riot 规则文字），但模式照样提升。所以起作用的是**描述**，不是调用时用的名字。
3. **补上「破坏性操作先问」没有副作用**：B4 和 B1a 相当，长期进程没放后台的次数还从 4 次降到 0 次。
4. **正确率、改动追踪、成本都不受影响**：100% 通过，代码改动 100% 走 Write/Edit/Delete，token 略少。

**结论：B4 可以落地。** riot-tools 需要做的事：

- DeepSeek 下用 `bash` 工具：描述是 RL 原文加「破坏性操作先问」一条，参数只有 `command`；
- 持久 shell 语义：cwd 和导出的环境变量跨调用保留；
- 用 `&` 放后台的进程由 Riot 托管，会话结束时回收（要能找到 `nohup` / `setsid` 逃出进程组的进程）；
- 对 `Bash` 的调用按别名路由到 `bash`；
- 其余工具不动。

### 8.12 落地与真实请求回归（E9、E10）

**E9：工具名的影响**（`e9_probe.py`，单步，修 bug 各 24 次）：T0 是 4/24，RL 描述配小写 `bash` 是 16/24，配 `Bash` 是 17/24。名字不影响效果，所以落地时**保留 `Bash`**。权限规则、hooks、闸门、分类器都按这个名字认，一个都不用改。

**实现**：

- `riot-permissions/src/bash/background.rs`：`split_background` 用 tree-sitter 找出顶层以 `&` 结尾的语句。嵌套在子 shell、代码块、循环里的 `&` 不拆，有 heredoc 的命令也不拆。
- `riot-tools/src/tools/rl_bash.rs`：`RlBash`。
  - 名字是 `Bash`，参数只有 `command`，schema 手写、和 RL 环境逐字一致；
  - 描述是 RL 原文加「破坏性操作先问」，超时 300 秒；
  - 每次执行时用包装脚本恢复 cwd 和导出变量，执行完把新状态打在 stdout 末尾，内核解析后按会话存在内存里（会话删除时清掉）；
  - 顶层 `&` 的语句进终端面板，其余语句按顺序前台执行；
  - 权限判定逐段进行：都放行才放行，有一段拒绝就拒绝，其余情况按整条命令、后台口径再判一次；
  - 权限判定、沙箱、`bash_effects` 改动追踪、输出裁剪都复用标准 Bash（`bash.rs` 里抽出了 `decide_command`，超时提示加了 RL 版写法）。
- `PromptProfile::rl_shell`：DeepSeek 打开，主循环用 `use_rl_shell` 把 Bash 换掉。子 agent 用自己写死的工具集；分叉沿用父会话的工具，但会话 id 是各自的 agent id，shell 状态不会串。
- **工具顺序**：两个协议都按名字给工具排序。新增 `lead_tools` 配置（`riot_providers::lead_tools_first`），DeepSeek 开 `rl_shell` 时把 `Bash` 固定排第一，其余仍按名字排序，顺序依旧确定。

**真实请求回归中发现的问题**：第一版落地后导出真实请求一测，修 bug 只有 5/24，和改之前一样。拆开后发现两处和探针不同（单步，修 bug 各 24 次）：

### 8.13 撤回：恢复标准 Bash（2026-10-18）

RL 式 Bash 已经整体撤回，代码里不再保留。DeepSeek 主循环恢复使用标准 Bash，规则后置（R2）保留。

**撤回原因**：RL 式 Bash 只有 `command` 一个参数，拿掉了标准 Bash 的几项产品功能：

- `background: true`：长期服务进终端面板，由 Riot 管理；
- `run_in_background: true`：会自己结束的长命令放到后台，跑完自动通知模型；
- `sandbox: false`：被沙箱拦截时，由模型申请、用户确认后出沙箱。

用 `&` 加终端面板只能替代第一项，后两项没有等价物。实验指标（推理模式、正确率、改动追踪）只覆盖了模型这一侧，没有把这些产品功能的损失算进去。这是评估上的缺口，不是实验数据有误。

E9 和 E10 的数据（工具名无关，工具顺序和 schema 有关，真实请求下首步简写 17% → 69%）仍然有效，可以作为以后的参考。

### 8.14 下一步

1. **保住功能的 Bash 描述**（如果还想要这部分收益）：参数保持不变（`background`、`run_in_background`、`sandbox`、`timeout_ms`、`description`），只改写描述的写法和长度，向 RL 原文靠拢（短，没有大段禁令），并且排在第一位。用 `wire_compare.py` 和 `e10.py` 回归，同时把这些参数的正确使用纳入检查。
2. **精简但保留约束的工具描述**（可选）：每个工具只留两三句最关键的「什么时候用、什么时候别用」（比如 Glob / Grep 代替 `find` / `grep`，Read 代替 `cat`），删掉示例和长篇说明。看能不能落在 T0 和 T2 之间：模式接近 T2，纪律接近 T0。
3. **更难的 agent 任务集**：现在的任务对最高档的 flash 太简单。需要多文件、需要先定位问题、描述模糊的 bug（比如从真实项目的提交历史里回放），才能让正确率拉开差距。
4. **设计题加评审**：第二个评审（人或另一家模型）加上交换左右位置的二次评分，把 9 题扩到 30 题。
